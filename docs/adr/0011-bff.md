# 0011 — Backend for Frontend (BFF): fora da V1, revisto no backoffice

- **Status:** Aceito
- **Data:** 2026-10-08

## Contexto

Um BFF é uma camada de servidor dedicada a um cliente: adapta a API às telas daquele cliente, agrega chamadas e, em clientes web, guarda os tokens no servidor, de modo que o navegador recebe só um cookie `httpOnly`.

A pergunta surgiu na semana 5, com o Pix em construção: vale introduzir um BFF agora, e valeria ter modelado o projeto com BFF desde o início?

Forças em jogo:

- A V1 tem um único cliente, o app Flutter. O backoffice web é a Fase 3 (`roadmap.md`, seção 10).
- A API já nasce com o formato do app: rotas por tela (`/v1/me`, `/v1/me/account`, o Pix em passos que seguem as telas 7 a 10), DTOs mínimos (READ-02) e um contrato gerado que quebra o build se divergir (ADR 0008).
- No app, os tokens ficam no Keychain/Keystore (MOB-01). O principal ganho de segurança do BFF é tirar tokens do JavaScript do navegador, o que não se aplica ao mobile.
- Os orçamentos de performance são medidos: p95 abaixo de 200 ms nas leituras e de 400 ms no Pix (CLAUDE.md, seção 6).
- O escopo da V1 está congelado desde 2026-10-05, e nenhuma estrutura entra antes de existir código que precise dela.

## Opções consideradas

1. **BFF dedicado para o app, já na V1.**
   - ➕ Isola a API central de mudanças de tela e permite agregar dados por tela.
   - ➖ Acrescenta um salto de rede em toda chamada, inclusive no Pix.
   - ➖ Acrescenta um serviço para autenticar, limitar, registrar em log sem dados pessoais e cobrir no threat model e no ASVS.
   - ➖ A `Idempotency-Key` e o `requestId` precisam atravessar duas camadas sem erro.
   - ➖ Acrescenta mais um deploy.
   - ➖ Não traz ganho de segurança para o mobile.
2. **BFF desde o início do projeto.**
   - Teria os mesmos custos da opção 1, desde a semana 1.
   - Só se justificaria se o escopo inicial tivesse vários clientes (internet banking web, backoffice na V1), vários times donos de telas ou microsserviços. O ADR 0002 descartou microsserviços.
3. **Sem BFF na V1: a API do monólito é a borda do app, e o assunto volta no backoffice.**
   - ➕ A camada `http/` de cada módulo já fala a língua do app, e o domínio não conhece o app. É o benefício do BFF, uma API sob medida, sem um processo a mais.
   - ➖ Se o app passar a precisar juntar dados de vários contextos numa tela, a API ganha rotas de leitura por tela. Isso continua sendo um ponto único para as telas evoluírem.

## Decisão

**Opção 3.** Nenhum BFF na V1.

- Quando uma tela precisar de dados agregados (por exemplo, a Home com saldo e últimas movimentações, na semana 6), a solução é uma rota de leitura na própria API, não um serviço novo.
- **Revisão obrigatória no desenho da Fase 3 (backoffice).** O desenho atual do backoffice já tem o formato de um BFF: o servidor do Next.js mantém a sessão do staff em cookie `httpOnly`, Server Components e Server Actions chamam a API `/admin/*` privada pela rede interna, e o navegador nunca recebe um token (`roadmap.md`, seção 10).
- **Perguntas da revisão:**
  1. O servidor do Next.js basta como BFF do backoffice, ou é preciso um serviço dedicado?
  2. Como ficam CSRF e `SameSite` nas Server Actions? Esse item está marcado como "reavaliar no backoffice" na matriz de controles.
  3. Como o `requestId` e a `Idempotency-Key` dos comandos do staff (estorno, desbloqueio) chegam à API?
- **Gatilhos para rever antes da Fase 3:**
  - um segundo cliente com necessidades diferentes do app (internet banking web, app de parceiros);
  - uma tela que precise de várias chamadas e passe do orçamento de p95, medido, não estimado.

## Consequências

- ➕ Nenhum salto de rede extra no caminho do Pix, nem serviço a mais para proteger, monitorar e implantar na V1.
- ➕ A idempotência e o `requestId` continuam com um único ponto de entrada.
- ➕ A porta continua aberta: um BFF futuro entra como mais um cliente da mesma API e do mesmo contrato, sem mudar o domínio.
- ➖ A API do monólito acumula rotas desenhadas para as telas do app. Se surgir um segundo cliente com outras telas, elas precisarão ser separadas ou duplicadas na borda.
- ➖ A decisão depende de a revisão realmente acontecer no desenho da Fase 3. Por isso o item está no roadmap, seção 10.
