# next bank — Diagramas C4

Visão da arquitetura em dois níveis do modelo C4: **contexto** (quem usa o sistema e com o que ele conversa) e **containers** (as peças que rodam e como se comunicam). O nível de componentes está no [modelo de domínio](domain-model.md) (contextos e agregados) e no [ADR 0002](../adr/0002-monolito-modular-ddd-hexagonal.md).

## Nível 1 — Contexto

```mermaid
flowchart TB
    CLI["👤 Cliente<br/><i>pessoa física</i>"]
    OPE["👤 Equipe do banco<br/>operador, analista, admin"]

    NB["🏦 next bank<br/>conta, saldo, Pix, extrato, backoffice"]

    BACEN["Sistema de pagamentos<br/>(simulador do Bacen: SPI e DICT)"]
    SEN["Sentry<br/>monitoramento de erros"]

    CLI -- "usa o app" --> NB
    OPE -- "opera pelo backoffice" --> NB
    NB -- "envia e recebe Pix externos" --> BACEN
    NB -- "erros sem dados pessoais" --> SEN
```

| Elemento | Papel | Desde |
|---|---|---|
| Cliente | Abre conta, consulta saldo e extrato, faz Pix, paga por QR Code, recarrega o celular | `v1.0.0` |
| Equipe do banco | Consulta clientes com dados mascarados, bloqueia contas, estorna Pix e resolve a conciliação, com dupla aprovação | `v1.3.0` |
| Sistema de pagamentos | Liquida Pix entre instituições, de forma assíncrona e sujeita a falhas; o simulador falha de propósito | `v1.2.0` |
| Sentry | Recebe erros e falhas, sem dados pessoais | `v1.0.0` |

## Nível 2 — Containers

```mermaid
flowchart LR
    subgraph DEVICE["Aparelho do cliente"]
        APP["📱 App mobile<br/><b>Flutter</b><br/>Riverpod · Dio<br/>tokens no Keystore"]
    end

    subgraph VERCEL["Vercel"]
        BO["🖥️ Backoffice<br/><b>Next.js</b> (BFF)<br/>Server Components e Server Actions<br/>sessão em cookie httpOnly"]
    end

    subgraph RENDER["Render: um serviço Node.js"]
        API["⚙️ API<br/><b>Fastify + TypeScript</b><br/>monólito modular<br/>/v1 (app) · /admin/v1 (equipe)"]
        WRK["🔁 Laços em segundo plano<br/>outbox · consulta de status<br/>conciliação · agendamentos"]
        SIM["🏛️ Simulador do Bacen<br/>SPI e DICT, montado em /simulator"]
    end

    subgraph NEON["Neon"]
        DB[("🗄️ PostgreSQL 17<br/>schema por contexto<br/>ledger e auditoria só por inclusão")]
    end

    APP -- "HTTPS / JSON<br/>Bearer + Idempotency-Key" --> API
    BO -- "HTTPS<br/>chave do backoffice + token da equipe" --> API
    API -- "SQL · TLS<br/>papel nextbank_app" --> DB
    WRK -- "lê o outbox" --> DB
    WRK -- "envia Pix" --> SIM
    SIM -- "webhook assinado (HMAC)" --> API
    SIM -- "SQL · TLS<br/>papel próprio" --> DB
```

| Container | Tecnologia | Responsabilidade | Desde |
|---|---|---|---|
| App mobile | Flutter | Interface do cliente; nunca decide saldo nem autorização | `v1.0.0` |
| API | Fastify + TypeScript | Regras de negócio e integridade financeira, em módulos por contexto; as rotas `/admin` da equipe ficam no mesmo serviço, protegidas em camadas (STF-08) | `v1.0.0` |
| PostgreSQL | Neon | Fonte da verdade; última barreira das invariantes financeiras | `v1.0.0` |
| Laços em segundo plano | Node.js, no processo da API | Entrega do outbox ao SPI, consulta de status, conciliação diária e agendamentos ([ADR 0016](../adr/0016-outbox-e-inbox.md), [0018](../adr/0018-pix-assincrono-e-conciliacao.md)) | `v1.2.0` |
| Simulador do Bacen | Fastify, no serviço da API | Imita o SPI e o DICT: latência, falhas e confirmação assíncrona ([ADR 0017](../adr/0017-simulador-no-servico-da-api.md)) | `v1.2.0` |
| Backoffice | Next.js na Vercel | Ferramenta interna da equipe; BFF com sessão em cookie ([ADR 0011](../adr/0011-bff.md), [0020](../adr/0020-ui-do-backoffice.md)) | `v1.3.0` |

O desenho original previa o worker, a API administrativa e o backoffice como serviços separados no Render. A hospedagem gratuita mudou isso: um segundo serviço dividiria as horas gratuitas da API, e o serviço privado é pago. As consequências estão nos ADRs 0012, 0016 e 0017 e no plano da `v1.3.0` (B1).

## Implantação da V1

Como a V1 roda em produção, sem custo (ADR 0012; passo a passo em `docs/operations.md`):

```mermaid
flowchart LR
    APP["📱 App Android<br/>APK das Releases"]

    subgraph EDGE["Internet"]
        CF["☁️ Cloudflare<br/>TLS e borda do Render"]
    end

    subgraph RENDER["Render · us-east-1 · plano gratuito"]
        PRX["🔀 Proxy do Render"]
        API["⚙️ API pública<br/>Node 24 · Fastify<br/>TRUST_PROXY=3"]
    end

    subgraph NEON["Neon · us-east-1 · Postgres 17"]
        DEMO[("🗄️ branch demo<br/>dados da demo")]
        CLEAN[("🧊 branch clean<br/>papéis e banco vazio")]
    end

    subgraph GH["GitHub Actions"]
        DEP["deploy.yml<br/>migrations → deploy → smoke"]
        RST["demo-reset.yml<br/>diário, 06:00 UTC"]
        REL["release.yml<br/>tag v* → APK"]
    end

    SEN["🚨 Sentry<br/>só erros, sem PII"]
    AWK["⏰ UptimeRobot<br/>/health a cada 5 min"]

    APP -- "HTTPS" --> CF --> PRX --> API
    API -- "TLS verify-full<br/>nextbank_app, pooler" --> DEMO
    DEP -- "migrations<br/>nextbank_migrator" --> DEMO
    DEP -- "deploy hook" --> API
    RST -- "demo ← clean" --> DEMO
    RST -. "seed pela API" .-> API
    AWK -. "/health" .-> API
    REL -. "APK + SHA-256" .-> APP
    API -. "erros inesperados" .-> SEN
    APP -. "erros inesperados" .-> SEN
```

**Neste diagrama, tudo já está em produção.** Linhas sólidas: o caminho de cada requisição e de cada mudança. Linhas tracejadas: chamadas agendadas ou assíncronas.

| Peça | Papel |
|---|---|
| Cloudflare e proxy do Render | Terminam o TLS e repassam ao serviço; a API confia em exatamente três saltos para achar o IP do cliente (API-14) |
| Branch `clean` | Papéis, permissões e banco vazio; nunca recebe dados |
| Branch `demo` | Recriado a partir do `clean` todo dia; nenhum código apaga lançamentos do ledger |
| GitHub Actions | Único caminho de mudança em produção: migrations antes do código, smoke test depois |
| Sentry | Erros inesperados da API e do app, limpos de dados pessoais antes de sair |
